# Persistence and Migration Contract

Status: Accepted foundation contract.

## Purpose

ConstructFlow project data must survive SketchUp save/reopen, application upgrades, module upgrades and library changes without becoming dependent on chat history or an external database being online.

## Persistence layers

### 1. SketchUp model-local semantic data

Store the minimum authoritative semantic envelope and domain payload required to reopen the project in the `.skp` model using namespaced metadata and recoverable entity references.

Must include:

- smart-object stable IDs;
- object type and owner module;
- schema versions;
- phase lifecycle;
- level references;
- domain parameters required to regenerate behavior;
- relationships/connectors sufficient for project reconstruction;
- catalog references plus project-safe snapshot metadata;
- geometry ownership markers.

### 2. Project index/cache

ConstructFlow may maintain model-local indexes for fast lookup of object IDs, types, relationships and dirty state. Indexes are rebuildable and must not be the only copy of irreplaceable semantic data.

### 3. External/project database

Future cloud/local project databases may store richer history, rate libraries, collaboration, catalog metadata, drawing issues and analytics. The `.skp` project must still fail gracefully and remain semantically readable when external services are unavailable, subject to explicitly cloud-only features.

## Namespaces

Core envelope: `constructflow.core`  
Domain payload: `constructflow.<module>`  
Library reference/snapshot: `constructflow.library`

A module may not write another module's private namespace directly.

## Stable identity

SketchUp entity IDs are not ConstructFlow object IDs. Stable IDs are generated by ConstructFlow and persist across sessions.

Geometry children may change when a parametric object regenerates while semantic object ID remains stable.

## Geometry regeneration

A domain object should be able to distinguish:

- semantic state;
- generated geometry state/version;
- manual/legacy geometry where conversion rules allow it.

Regeneration must preserve object ID and compatible relationships. If user edits raw child geometry in a way the module cannot safely absorb, the object should be marked modified/invalid or require `Convert/Detach/Repair`, not silently discard semantic state.

## Save behavior

Before model save, runtime should ensure pending semantic transactions are committed and required envelope data is serializable. Heavy derived caches need not all be persisted if safely rebuildable.

## Load behavior

Suggested order:

1. boot Core;
2. discover/load module manifests;
3. scan/rebuild smart-object index;
4. validate core envelope versions;
5. run required migrations;
6. allow domain modules to validate/rebuild caches;
7. resolve relationships/connectors;
8. mark unresolved objects rather than deleting them;
9. expose model health diagnostics.

## Unknown/unavailable module

If a project contains objects owned by an unavailable module:

- preserve its namespaced data;
- preserve geometry where possible;
- show object as unsupported/read-only placeholder;
- do not delete private payload;
- allow module reinstall/upgrade to recover behavior.

This is essential for modularity.

## Schema versioning

There are separate versions for:

- core smart-object envelope;
- each module object type/schema;
- command/event contracts;
- catalog assets;
- application release.

Do not conflate them.

## Migration contract

Each owner module provides deterministic migrations for its persisted schema:

```text
v1 → v2
v2 → v3
```

Migration must:

- declare source and target versions;
- preserve stable object identity unless an explicit split/merge migration is documented;
- preserve unknown fields owned by other namespaces;
- validate result;
- be covered by fixture tests;
- not silently fabricate missing engineering/site facts.

## Split/merge migrations

If one legacy smart object becomes multiple semantic objects or vice versa, migration must document identity mapping and relationship repair.

Example:

`LegacyRoof` may become `RoofSystem + RoofCovering`, but the migration must establish `generated_from/contains` relationships and preserve references used by drawings/quantities as much as possible.

## Project backup

Before a destructive or non-reversible migration, ConstructFlow should provide/require a recoverable project copy or transaction-safe backup mechanism appropriate to SketchUp runtime limitations.

## Catalog snapshots

Placed assets store enough local information to remain usable:

- asset ID/version;
- variant;
- essential dimensions/parameters;
- geometry/component definition or recoverable embedded representation;
- key specification metadata used by project outputs.

A catalog update is never a hidden model migration.

## Drawing/quantity persistence

Derived quantities/drawings can cache results and source revision/hash metadata, but current smart-object state remains authoritative. If source state changed, cached output becomes dirty rather than silently reused.

## Corruption handling

On invalid metadata or broken references:

- do not delete data automatically;
- mark object `invalid`/`orphaned`;
- expose diagnostics;
- offer repair command when deterministic;
- permit export/inspection of raw namespaced metadata in developer/support mode.

## Foundation migration acceptance

At minimum, tests must prove:

1. v1 object persists through save/reopen;
2. synthetic old schema migrates to current version;
3. repeated load does not reapply completed migration incorrectly;
4. missing optional module preserves its data;
5. restored module can rehydrate object behavior;
6. catalog source unavailable does not destroy placed assets.
